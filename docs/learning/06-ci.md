# Phase 6: Continuous integration

## Goal

Every pull request automatically builds the backend, builds the frontend, and
runs all 364 tests, on a clean machine, without anyone remembering to.

## Why it matters

The tests already existed and already passed. So what does automating them buy?

**It removes the human.** During this project a dependency update reported
success, produced a valid-looking lockfile, and compiled fine. It had also
silently deleted a package the tests needed, and 36 of 37 frontend test files
failed to load. That was caught only because the suite happened to be run.
Trivial-looking changes are exactly where the discipline slips.

**It runs on a machine that is not yours.** A laptop has global packages, warm
caches, environment variables, and a database already running. `ubuntu-latest`
has none of that. CI is the closest available answer to "does this work for
someone who is not me", which is the question a public repository has to survive.

## Concepts

### CI is not CD

These get said as one word and are three different things.

| Term | Meaning |
|---|---|
| Continuous integration | Every change is built and tested automatically |
| Continuous delivery | Every green build is *deployable*; releasing is a decision |
| Continuous deployment | Every green build deploys itself, with no human step |

Most teams that say "CI/CD" mean integration plus delivery. Very few deploy to
production automatically on every merge.

### Reporting versus enforcing

A workflow that runs on a pull request only *reports*. Until the repository
requires those checks to pass, a red build can still be merged. Required checks
are a repository setting, not a workflow setting, and they are what turn CI from
a smoke alarm into a lock on the door.

GitHub does not offer branch protection on free private repositories. This one
therefore reports today and will enforce when it becomes public.

### Why `npm ci` and not `npm install`

`npm install` resolves dependencies and may update the lockfile. `npm ci`
installs exactly what the lockfile pins, and fails outright if `package.json`
and `package-lock.json` disagree.

In CI that difference is the whole point: `install` means CI might test
different versions than a developer ran locally, which makes a green build
meaningless. It is also faster, because it skips resolution entirely.

### Fail fast, and cheaply

Three settings in this workflow exist purely to control cost and noise:

- `concurrency` with `cancel-in-progress` kills superseded runs. Push twice in a
  minute and the first run stops, instead of spending minutes on a result nobody
  will read.
- `timeout-minutes: 15` per job. GitHub's default is six hours. A hung job would
  otherwise consume an entire month's budget on a private repository.
- `permissions: contents: read`. The default token can write to the repository.
  These jobs only read it. Start narrow and widen when a job genuinely needs more.

## What is already here

`.github/workflows/ci.yml` runs two jobs in parallel on every pull request into
`main`, and on every push to `main`.

```
backend    dotnet restore -> build (Release) -> test        97 tests
frontend   npm ci -> lint -> build -> test                 267 tests
```

They are separate jobs, not steps in one job, so they run at the same time and a
frontend failure does not hide a backend failure.

**No database service is configured.** The integration tests use Testcontainers
and start their own SQL Server container. `ubuntu-latest` ships with Docker, so
the tests manage their own dependency. See [Phase 7](07-testing.md).

**No NuGet caching.** `setup-dotnet` keys its cache off `packages.lock.json`, and
this solution does not use NuGet lock files. Enabling caching without them fails
the job. Adding lock files is worthwhile but is a separate change.

## Tasks

### 1. Read a real run

```bash
gh run list --workflow=ci.yml --limit 5
gh run view --log
```

Find how long each job took and which step dominated. Knowing where the time
goes is what lets you make a pipeline faster later.

### 2. Watch it fail on purpose

Understanding a green pipeline is easy. Learn to read a red one.

```bash
git checkout main && git pull
git checkout -b experiment/break-ci
```

Break one test deliberately — change an assertion in
`tests/UnitTests/CourseRulesTests.cs` so it cannot pass. Then:

```bash
git add -A
git commit -m "test: deliberately break a test to observe CI"
git push -u origin experiment/break-ci
gh pr create --fill
gh pr checks --watch
```

Read the failure in the Actions log. Notice that the frontend job still passes:
independent jobs isolate failures.

Then throw it away without merging:

```bash
gh pr close --delete-branch
git checkout main
```

Deliberately breaking things in a safe place is how you learn to read failures
under pressure later.

### 3. Add a status badge

At the top of the root `README.md`:

```markdown
![CI](https://github.com/NoahStarkenburg/knowledge-market/actions/workflows/ci.yml/badge.svg)
```

It renders the current state of `main`. On a portfolio repository it signals that
tests exist and pass, which most repositories cannot claim.

## Verify

```bash
gh run list --workflow=ci.yml --limit 3
```

Every run on `main` should be `success`.
